DSec：让海量有状态沙盒低成本地持续存在

把环境构建、资源占用与执行状态分开管理：环境可复用，资源按需用，Rollout 状态不依赖 GPU 训练作业的生命周期。

核心观察：沙盒常在等待模型生成下一步操作，但文件、进程与内存状态不能随之丢弃。

资源错配：约 90% 的沙盒，平均 CPU 用量不超过申请量的 5%；低 CPU 活跃度并不等于低状态保持成本。[1]

环境拆开复用：Base、Workspace 与 Toolkit 独立版本化，运行时组合；更新一个工具层，不必重建所有任务镜像。[1]

资源按需占用：镜像数据从 3FS 按访问需要加载；配合内存共享、回收与 CPU 服务质量控制，提高沙盒部署密度。[1]

状态独立保留：将 Agent Loop 的执行与管理移到可抢占 GPU 池之外。旧方案中沙盒虽仍存在，Agent Loop 却会丢失；新方案由 Worker 与 Agent Sandbox 共同保留 Rollout 状态，训练作业恢复后重新连接。[1]

研究启发：计算资源的生命周期，不必等于有状态环境的生命周期。

EBRL：让仿真、动作生成与训练持续重叠

只让 Rollout 与 Training 异步还不够：还要消除环境之间不必要的同步，并把资源分配细化到 CPU 核与 GPU 逻辑算力配额。

核心问题：整卡独占与批量同步让快环境等慢环境、推理等仿真；各阶段需求还会随训练进展改变，固定分配容易失衡。[2]

跨迭代：采集新轨迹的同时，使用先前轨迹更新模型。

跨环境组：一组执行已有动作，另一组生成下一段动作，让仿真与动作生成重叠。[2]

跨仿真步：各环境已拿到一段动作，可在段内独立推进，不必每步等待其他环境。

释放即调度：等待新动作的环境释放 CPU 核，交给其他就绪环境；优先调度预计较慢的步骤。[2]

资源随瓶颈调整：基于离线 Profile 与运行时吞吐反馈，选择 CPU 核数、GPU 逻辑 SM 配额和 Batch Size，平衡仿真、生成、训练的处理能力。默认通过 MPS 支持共享执行。[2]

依赖仍需保留：环境只能在已有动作范围内提前推进；下一段动作仍依赖新观测与模型生成。异步不是跳过因果关系。[2]

论文结果：所测配置的端到端轨迹吞吐达到基线的 1.30–3.47 倍；收益依赖具体模型、仿真器与硬件。[2]

研究启发：不仅要让更多任务并行，还要让可执行工作与合适的资源及时匹配。

三个值得探索的切入点

以下均为研究设想；图中布局与收益方向是概念示意，不代表已实现或实测结果。示意图依据会议 TeX 原图改为网页排版。

A　有状态仿真环境的弹性暂停与恢复

核心思想：将仿真状态与计算资源解耦：在一致性边界保存动态物理状态、随机状态和 Rollout 进度，资源恢复后从断点继续，而不是重新初始化并重跑轨迹。

新问题与难点：从 DSec 的 Agent 状态扩展到物理仿真状态；关键是哪些内部状态可恢复、恢复后是否足够一致，以及保存成本是否低于重跑成本。

B　感知 RT 渲染与数据搬运的异构 GPU 调度

核心思想：不只按 SM 配额分配资源，而是联合考虑 RT 渲染需求、SM、显存与跨设备传输，动态选择仿真、推理、训练的同卡共享或跨卡拆分。

新问题与难点：EBRL 已测试 RTX + A100 混合配置；新意不在“使用异构 GPU”，而在渲染干扰与通信成本驱动的动态布局。RT 需求感知也不等于已能直接切分 RT Core。[2]

C　可组合、可复用的仿真场景缓存

核心思想：共享静态场景资产与可复用的初始化产物，为每个环境保留独立动态状态；按任务切换模式缓存或预加载，减少场景加载和重复初始化。

新问题与难点：从 DSec 的软件镜像层扩展到仿真场景生命周期；核心是跨任务能共享什么、版本变化如何失效，以及收益能否超越普通镜像缓存与单次进程内复用。

三个方向的分工：A 管“状态如何留下”，B 管“计算放到哪里”，C 管“环境如何复用”。
